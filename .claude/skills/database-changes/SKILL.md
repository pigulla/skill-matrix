# Database Changes

## Overview

Persistence is an **infrastructure-layer output boundary**. It may import from Domain and from Application interfaces/errors only — never the reverse. The domain must not know how data is stored.

Request flow: `Driving port (presentation — controller, CLI, …) → Domain interface → Repository impl (infrastructure) → PostgreSQL`. The HTTP controller is the only driving port today; others (e.g. a CLI) may be added.

Stack: **pg-promise** for queries, **@nestjs-cls/transactional** for transactions, **node-pg-migrate** (SQL migrations), **Zod** for row validation, **Testcontainers** for tests.

## Where things live

| Concern                                          | Location                                                         |
| ------------------------------------------------ | ---------------------------------------------------------------- |
| Repository interface (abstract class = DI token) | `src/domain/<entity>/<entity>.repository.interface.ts`           |
| Repository implementation                        | `src/infrastructure/persistence/<entity>/<entity>.repository.ts` |
| SQL statements (one file per query)              | `src/infrastructure/persistence/<entity>/sql/*.sql`              |
| Query registry                                   | `src/infrastructure/persistence/<entity>/sql/queries.ts`         |
| Row schema + `toDomain()`                        | `src/infrastructure/persistence/<entity>/sql/<table>.row.ts`     |
| Migrations                                       | `migrations/<timestamp>_<name>.sql`                              |
| pg error helpers / codes                         | `src/infrastructure/persistence/error/`                          |

## Non-negotiable rules

- **No inline SQL strings.** Every statement lives in its own `.sql` file under `sql/`, is registered in `queries.ts` via `queryFiles(import.meta.dirname, [...])`, and is referenced through the generated `QUERY` object. The only exception is throwaway SQL inside integration tests (`db.one('SELECT ...')`).
- **Named parameters only** — `$(id)`, never positional `$1`. SQL columns are `snake_case`; map to/from `camelCase` domain fields explicitly in the repository call and the row schema.
- **Validate every row with Zod** before returning. Query into `unknown`, then `xxxRow.parse(row).toDomain()`. Never cast a raw row to a domain type.
- **Wrap every query in try/catch.** Re-throw unknown failures as `UnexpectedPersistenceError`. Translate expected PostgreSQL errors into domain errors (e.g. unique violation → `Duplicate*Error`) using the helpers in `error/`. Never leak a raw pg error past the boundary.
- **`get*` throws, `find*` returns `null`.** A `get`-prefixed method must always return the entity (or entities) and throw the entity's `*NotFoundError` when it does not exist — never return `null`. A `find`-prefixed method may return `null` (or an empty result) for a missing entity and must never throw `*NotFoundError`. In both cases query with `oneOrNone` and branch on the `null` result accordingly (see the user repository for the `get` pattern).
- **Transactions are declared in the application layer** with `@Transactional()` on the service method — not in the repository. Repositories always read/write via `this.txHost.tx`. Serializable isolation is the default (`default-transaction-options.ts`). **Exception:** a repository method that itself issues multiple related writes (e.g. an insert followed by rebuilding a join-table association) may carry its own `@Transactional()` so it stays atomic when invoked on its own — see `SkillRepository.create()`/`update()`. This nests safely under a service-level `@Transactional()` because `@nestjs-cls/transactional`'s default propagation is `Propagation.Required`: it joins the already-open transaction instead of starting an independent one. Don't add `@Transactional()` to a repository method that issues only a single statement — it's already atomic and the decorator adds nothing.
- **Errors are classes** (`*.error.ts`), never plain strings. Domain not-found and constraint-violation errors live in `src/domain/<entity>/`.
- **Explicit naming.** Always make the names for primary keys, indices and constraints explicit. They must remain stable even if the default names generated by Postgres change.
- **Format & lint SQL.** Run `npm run format:sql` after editing any `.sql` file; `npm run lint:sql` runs as part of the lint suite.
- **`.sql` files are copied into `dist/` at build time** (`npm run build:copy-sql`). Keep them as real files on disk; do not build SQL strings dynamically.

## Common mistakes

- Inlining a SQL string in the repository instead of adding a `.sql` file + `queries.ts` entry.
- Returning `null` from a `get*` method instead of throwing `*NotFoundError` (or throwing `*NotFoundError` from a `find*` method, which should return `null`).
- Casting a row (`row as User`) instead of `xxxRow.parse(row).toDomain()`.
- Putting `@Transactional()` on a repository method that issues only a single statement (already atomic; the decorator adds nothing), or opening a transaction manually. Only warranted when a repository method spans multiple related writes that must succeed or fail together.
- Forgetting to translate a unique-constraint violation into a domain error (raw pg error leaks).
- Editing `.sql` and skipping `npm run format:sql` (fails `lint:sql`).
- Importing infrastructure types into the domain (fails the Clean Architecture check, `npm run lint:architecture`).
